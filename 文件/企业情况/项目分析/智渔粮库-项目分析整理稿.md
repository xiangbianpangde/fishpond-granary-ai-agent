# 空天渔场与无人化粮库 AI 智能体项目分析（整理稿）

> 用途：内部对齐，统一团队对**两个模块的边界、推进顺序和 Demo 选型**的理解。
> 状态：以渔业模块的深度为参考，粮库模块已补齐到相近深度；企业标准、政府对接细节等未知项均标为 `待确认`。
> 原始背景稿：`20260624智渔粮库.md`（保留为正式对外材料来源，本稿用于内部整理）。

## 一、背景

### 1. 现状

1. 我司已完成**空天渔场**、**无人化粮库**两大场景的物联网硬件铺设和基础信息化建设：
   1. 已具备数据采集、远程设备控制和阈值告警等基础能力；
   2. 系统整体仍以 **==“硬件自动化 + 人工决策”==** 为主。
2. 当前有三个主要瓶颈：
   1. ==缺少能够综合分析和辅助决策的 AI 中枢==，需要建设 **AI 决策层**；
   2. ==数据价值尚未充分释放==，需要整理 **行业知识和规则**；
   3. ==人工经验难以稳定复用==，需要逐步把原有人工流程改造成 **AI 辅助流程**。

> **补充判断**：企业当前的物联网建设程度仍需核实，系统可能尚未完整搭建或稳定使用。甲方似乎希望借助 AI 弥补物联网系统的不足，这一点必须在调研中确认。

### 2. 项目要求

1. 两大模块 ==共享底层能力、按场景独立运行==：共用技术底座，但分别交付、分别运行，单个模块故障不影响另一模块。
2. 分别解决水产养殖和粮食仓储的主要智能化痛点。
3. 推动流程从 ==“人工管控”逐步转向“AI 辅助决策”==，关键动作仍需受控。

### 3. 核心交付目标

本次只交付**一份 Demo**，用于向甲方技术负责人验证：

1. **技术可行性**：现有物联网基础、大模型 Agent 和行业规则，能否在两个场景中跑通“感知 → 决策 → 执行”闭环；
2. **痛点改善程度**：投喂粗放、监测盲区、夜间溶氧骤降、蟹病判断、粮情盲区、气调参数漂移、出入库账实不符、熏蒸期人员误入等问题，哪些可以实际解决或得到明显改善；
3. **推进路径**：Demo → 小范围试点 → 全量部署的路径是否合理。

> 预算与时间窗口：**待确认**（甲方未定）。

## 二、初步画像（系统分层）

```
[ 物联网感知层 ]        ← 现有；老旧仓房传感器可能存在漂移
        ↓
[ 数据平台层 ]          ← 情况待确认；Demo 阶段核实接入能力
        ↓
[ 专业 AI 模型层 ]      ← 新增（时序、视觉、异常检测、优化）
        ↓
[ 知识库和行业规则 ]    ← 新增
        ↓
[ 大模型 Agent 层 ]     ← 新增，负责综合判断和任务安排
        ↓
[ 决策建议 / 人机交互 / 任务编排 ] ← 新增
        ↓
[ 安全规则层 ]          ← 新增，负责权限、熔断和合规约束
        ↓
[ 原有设备控制系统 ]    ← 现有
        ↓
[ AI 辅助工作流 ]       ← 新增，承接部分人工判断和安排
```

**关键判断**：项目新增能力主要集中在数据平台之上、设备控制系统之下。物联网和设备控制是否真的可用，仍需先核实；Demo 阶段发现缺口时，应先补齐数据和接口，再推进 Agent。

## 三、模块一：空天渔场大模型养殖 AI 智能体

### 1. 场景基础

1. **场景定位**：连片、规模化、标准化水产养殖基地。
   1. ==初步判断：企业可能已有自己的养殖标准==，需要确认后再整理为行业规则（**企业标准细节待确认**）。
2. **核心作业模式**：通过跨塘架空索道和移动料仓定点投喂。
   1. 架空轨道覆盖各养殖塘口；
   2. 移动料仓沿索道到达指定点位并投料；
   3. 减少传统人工划船投料作业。

### 2. 硬件与系统基础

| 类别 | 已有项 | 备注 |
|---|---|---|
| 水质传感器 | 溶氧 / pH / 水温 多参数 | 多参数；接口情况待确认 |
| 视频 | 高清食台摄像头 | 食台区域覆盖；夜间覆盖能力待确认 |
| 设备 | 增氧机、智能控制柜 | 已可远程启停 |
| 气象 | 气象站 | 已接入 |
| 软件 | 渔业溯源软件系统 | 设备远程启停、数据可视化、阈值告警；**数据接口与设备接口细节待确认** |

### 3. 现存核心痛点

1. **投喂方式固定，调整效率低**
   - **现状**：索道系统按固定时间和数量投喂。
   - **需求**：
     1. 结合蟹苗生长阶段、实时水质和天气变化调整策略；
     2. 在高温、阴雨、低溶氧等特殊情况下及时给出建议，并完成允许范围内的维护动作。
   - **解决方向**：根据数据辅助调整投喂。
2. **多种数据没有形成合力**
   - **数据类型**：水质、视频、食台照片和气象。
   - **现状**：
     1. 目前难以全天候关联分析；
     2. 异常通常在发生后才被发现；
     3. 夜间、暴雨和高温等情况下存在监测盲区；
     4. 风险判断主要依赖个人经验。
3. **设备之间缺少联动**
   - **现状**：
     1. 设备系统**主要使用水质数据**，其他数据尚未联动；
     2. 设备更多只是辅助，判断仍靠人工经验；
     3. 响应较慢；
     4. ==夜间溶氧骤降，维护困难==（**核心高优痛点**）；
     5. 参数长期固定。
   - **需求**：
     1. 更快发现风险；
     2. 综合使用多种数据辅助判断；
     3. 将可复用的人工经验整理为行业规则。
4. **病害防控依赖个人经验**
   - **现状**：
     1. ==蟹病判断== 高度依赖资深养殖户；
     2. 缺少提前预警，等到肉眼可见时往往已经扩散；
     3. 处置方案缺少统一标准，同类病害由不同人员处理时差异较大，历史经验难以复用。
5. **数据统计和维护成本高**
   - **现状**：
     1. 生产、设备、能耗和病害数据分散在不同平台，养殖台账和监管报表也需要跨平台整理；
     2. 部分数据仍靠人工维护。

### 4. AI 能力解法（对应上述痛点）

1. **索道投喂辅助决策**——解决投喂固定、人工调参效率低的问题。
   - 综合考虑蟹苗生长周期、水温、溶氧、食台残饵照片和天气预报；
   - 按天、按塘口计算投饵总量、点位、时段和频次；
   - 在高温、阴雨、低溶氧等情况下识别应激风险，**建议下调或暂停投喂**，具体执行仍按权限处理。
2. **风险预警和研判**——解决数据分散、异常发现晚的问题。
   - 关联分析水质变化、视频/照片和气象数据；
   - 识别蓝藻爆发、外来人员闯入等视觉异常；
   - 根据历史变化识别溶氧骤降、水质恶化等趋势；
   - 给出风险等级、影响范围和处理优先级，并推送给相关人员。
3. **水环境调控辅助**——解决设备缺少协同、调控被动的问题。
   - 根据水质变化判断是否需要提前调控；
   - 按风险等级和塘口优先级安排设备启停顺序；
   - 对比调控前后的数据，评估效果并为后续规则调整提供依据。
4. **病害辅助研判和知识整理**——解决病害判断依赖经验、经验难复用的问题。
   - 将水质和环境情况与历史病例、行业标准进行检索比对；
   - 输出病害风险提示；
   - 生成标准化处置建议（水质改良、消杀、保健投喂），是否联动索道需按权限确认；
   - 将处置案例整理入库，便于后续复用。
5. **生产数据自动整理**——解决统计繁琐、效率低的问题。
   - 汇总生产、设备、能耗和病害数据；
   - 每日生成养殖台账，按月生成效益分析报告；
   - 支持用自然语言查询塘口和时段数据，减少跨系统人工汇总。

## 四、模块二：无人化粮库大模型仓储 AI 智能体

### 1. 场景基础

1. **场景定位**：**县级储备粮库**，承担地方储备粮的存储和周转。
   1. ==涉及政府授权==（**对接进展待确认**：监管口径、授权流程和数据上报规范）。
2. **仓房形态**：多座平房仓，另有部分改造的老旧仓房。
   1. 老旧仓房的**传感器可能存在漂移和精度不足**（与下文痛点 2.2 对应）。

### 2. 硬件与系统基础

| 类别 | 已有项 | 备注 |
|---|---|---|
| 粮情 | 仓内分层温湿度传感器 | 部分老旧仓房存在漂移 |
| 设备 | 智能电动通风窗、环流风机、气调储粮系统 | 已有远程控制能力 |
| 出入库 | 智能地磅、RFID 识别装置 | 一卡通系统下 |
| 安防 | 库区视频安防系统 | 烟火 / 周界 / 违章依赖人工回看 |
| 软件 | 粮库一卡通管理系统 | 基础粮情监测 + 设备远程控制 + 出入库台账登记；**接口细节待确认** |

### 3. 现存核心痛点

1. **粮情判断能力不足**
   - **现状**：
     1. 人工踏仓巡检频率低、劳动强度大；
     2. 熏蒸期和高温高湿期人员不能进仓，存在长期监测盲区；
     3. 传感器只能展示实时数据，难以提前发现粮堆发热、结露和虫害风险；
     4. 老旧仓房传感器可能漂移，影响判断可靠性。
   - **需求**：减少监测盲区，及时发现粮堆发热、结露和虫害风险。
2. **储粮调控较粗放**
   - **现状**：
     1. 机械通风、环流降温和气调杀虫主要靠人工操作；
     2. 调控时机和时长依赖保管员经验，可能通风不及时，也可能过度通风；
     3. 绿色气调参数控制不够准确，杀虫效果不稳定，参数难以持续调整。
   - **需求**：在安全前提下提供更准确的调控建议。
3. **出入库协同效率低**
   - **现状**：
     1. 扦样、质检、称重、平仓和入库登记之间数据不互通，需要人工传递单据；
     2. 多设备、多车辆依靠人工安排，收购旺季容易拥堵；
     3. 库存台账靠人工录入，可能出现账实不符，季度盘点工作量大。
4. **安全管控发现和响应较慢**
   - **现状**：
     1. 主要依靠保安巡逻和视频回看，烟火、翻越、违章作业、乱停乱放等问题不易及时发现；
     2. 熏蒸期间门禁缺少智能联动，**存在人员误入中毒风险**（**核心高优痛点**）；
     3. 药剂泄漏和设备故障缺少自动处置预案，应急响应依赖个人经验。
5. **经营数据统计繁琐**
   - **现状**：
     1. 储粮损耗、能耗、防虫药剂和运维成本分散在不同系统；
     2. 监管报表需要按月人工整理，数据口径不统一，也难以追溯。

### 4. AI 能力解法（对应上述痛点）

1. **粮情辅助研判**——解决风险发现晚、判断依赖经验的问题。
   - 接入仓内分层温湿度、仓外气象和历史数据；
   - 结合粮堆热湿传导规律和时序变化，识别发热、结露和虫害风险；
   - 对老旧传感器先做可信度评估，不在本阶段承诺自动校准；
   - 定位异常粮层和点位，输出风险等级与处置建议；
   - 为熏蒸期、高温期等人员不便进入的时段提供辅助监测。
2. **储粮环境调控辅助**——解决调控粗放、能耗和损耗难以控制的问题。
   - 综合仓内外温湿度、粮情状态、虫害等级和天气，判断通风或气调的合适时机；
   - 计算通风时长、气调浓度等建议参数，并按权限调用设备；
   - 跟踪调控过程，比较调控前后的粮情和能耗，评估策略效果；
   - 低碳储粮的持续优化属于后续能力，不能在 Demo 阶段过度承诺。
3. **出入库协同安排**——解决流程脱节和旺季效率低的问题。
   - 汇总仓容、库存、车辆预约和设备状态；
   - 生成作业计划，安排车辆顺序、仓房和设备；
   - 协调扦样设备、地磅、平仓机器人和转运设备；
   - 同步过程数据，核对库存台账，发现偏差后及时提醒。
4. **库区安全辅助防控**——解决安全发现晚、应急响应慢的问题。
   - 汇总视频、周界报警、气体传感器和门禁信息；
   - 识别烟火、翻越、熏蒸区域人员进入和药剂泄漏等风险；
   - 根据安全知识和处置预案生成建议，通知相关人员并调取现场画面；
   - 熏蒸期间的门禁和声光告警必须遵守原硬安全联锁及甲方 SOP，不能由 AI 直接替代；
   - 记录安全事件，便于后续复盘。
5. **储粮数据自动整理**——解决统计繁琐、监管报送效率低的问题。
   - 汇总粮食品质、损耗、能耗、防虫药剂和运维成本数据；
   - 自动生成季度和年度储粮管理报告；
   - 按监管数据规范生成台账（**政府对接细节待确认**，需进一步核对报送字段）；
   - 支持按仓房和时段查询数据，减少人工跨系统整理。

## 六、重点词汇解释

| 术语 | 一句话定义 | 与本项目的关系 |
|---|---|---|
| **自主决策** | AI 根据多种数据调整作业参数或提出设备动作 | Demo 需要验证的能力，但不等于完全无人操作 |
| **AI 工作流** | 由 AI 参与判断和安排的业务流程 | 本项目希望逐步承接部分人工工作 |
| **行业规则** | 从企业标准、行业标准和经验中整理出的可执行规则 | 知识库的重要组成部分 |
| **知识库** | 汇总行业标准、案例、SOP 和设备手册的资料库 | 支持检索和案例比对 |
| **多种数据** | 同时处理数值、图像、视频、文本和事件信息 | 渔业场景依赖较多，粮库也会使用 |
| **RAG（检索增强生成）** | 大模型先检索相关知识或案例，再生成回答 | 可用于病害判断、粮情研判和应急处置 |
| **时序预测** | 根据历史数据判断未来趋势 | 例如识别溶氧下降或粮堆发热趋势 |
| **CV（计算机视觉）** | 从图像或视频中识别目标和类别 | 例如识别残饵、烟火和违规行为 |
| **物理仿真模型** | 用数学和物理规律模拟对象变化 | 例如模拟粮堆热湿传导 |
| **智能补偿校正** | 用算法修正硬件误差 | 老旧传感器漂移场景的后续能力 |
| **安全规则层** | 规定权限、熔断和合规边界 | Demo 阶段必须明确，防止 AI 越权 |

## 七、两个模块各自面临的问题

### 1. 空天渔场

1. **数据问题**
   1. 生产、设备、能耗、病害、养殖台账和监管报表分散在多个平台；
   2. 目前主要使用水质数据，其他数据还没有联动；
   3. 人工经验没有整理成可复用的数据或规则，企业数据库和知识库仍不完整。
2. **平台问题**
   1. 平台尚未统一，业务环节多，接口复杂；
   2. 多个环节仍靠人工完成；
   3. 物联网真实建设程度需要先核实，之后才能判断 AI 工作流的推进节奏。
3. **场景复杂度**：对象是蟹等生物，生长阶段、水质、天气和应激相互影响，因此对模型的解释性和稳定性要求较高。
4. **技术组合较多**：需要结合数据处理、专业模型和 LLM，系统集成难度较高。
5. **人员风险**：项目可能引发岗位和经验归属方面的顾虑，Demo 前要先说明 AI 是协作和辅助，不是简单替代。

### 2. 无人化粮库

1. **数据问题**
   1. 粮情、设备、出入库、能耗、防虫药剂和运维数据分散在多个系统；
   2. 人工录入比例较高，库存台账长期存在账实不符风险；
   3. 老旧仓房传感器可能漂移，原始数据可信度不足。
2. **平台问题**
   1. 一卡通管理系统尚未与其他系统充分打通，业务环节脱节；
   2. 监管报表依赖人工整理，数据口径不一致；
   3. 安防系统与门禁、气体和设备的联动情况不明，安全事件处置较被动。
3. **场景复杂度相对低**：粮食本身相对静态，但热湿传导、虫霉滋生和气调反应等物理过程复杂，不能只靠数据驱动，需要结合机理模型。
4. **合规与安全要求高**：县级储备粮涉及政府授权、熏蒸人员安全和药剂管理，**所有 AI 动作都必须在合规边界内**，安全规则是硬约束。
5. **人员风险**
   1. 政府对接流程可能影响进度（**对接进展待确认**）；
   2. 保管员可能对自动化替代敏感，Demo 阶段要明确“AI 辅助”而不是“AI 替代”。

### 3. 两个模块的共性问题

1. 都以“硬件自动化 + 人工决策”为主，需要先评估物联网建设程度，再决定 AI 工作流的推进节奏；
2. 都需要行业知识，知识质量会直接影响 Demo 效果；
3. 都需要整合多个系统，数据接口是共同短板；
4. 都可能遇到人员配合问题，团队要先对齐“AI 是辅助还是替代”的边界。
