# 15 · AI 权限三维度模型（v0.4 新增 · Sol P0-3）

> **目的**：把"AI 是否能执行某动作"拆为 **技术权限 / 业务权限 / 安全权限** 三个独立维度，避免"技术可执行 = 业务允许执行"。  
> **必要性**：政府和粮库项目的真正风险不在技术，而在"技术能写"被误以为"业务允许写"。  
> **关系**：本模型在 `08_合规监管与责任画像.md` §2 Level 0–4 基础上做维度拆分；与 `09_AI价值机会画像.md` §3 ROI 指标联动。

## 1. 三维度定义

### 1.1 技术权限（Technical Authority）

> **定义**：AI 是否具备技术上调用该动作的能力（接口、协议、写权限、可执行）。

| Level | 含义 | 示例 |
|---|---|---|
| T0 | 无技术能力 | 没有接口或不在白名单 |
| T1 | 只读 | 能读取数据 / 状态 |
| T2 | 模拟写入 | 沙箱中能写入，真实不写入 |
| T3 | 真实写入 | 能对真实设备 / 系统写入 |

### 1.2 业务权限（Business Authority）

> **定义**：AI 是否具备业务上的授权（流程、角色、签字、风险等级）。

| Level | 含义 | 示例 |
|---|---|---|
| B0 | 无业务授权 | 业务未确认 / 不在 SOP |
| B1 | L0/L1 展示 + 建议 | 只展示 / 提建议 |
| B2 | 人工确认后执行 | 必须由人工触发（Level 2） |
| B3 | 白名单自动执行 | 白名单场景下的 Level 3 |
| B4 | 完全自动 | 不允许 Demo/Pilot |

### 1.3 安全权限（Safety Authority）

> **定义**：AI 在安全约束下是否允许执行（Safety Rule、原硬联锁、合规、监管）。

| Level | 含义 | 示例 |
|---|---|---|
| S0 | 禁止（监管红线） | 门禁、熏蒸、原硬联锁动作 |
| S1 | 仅通知 / 留痕 | Agent L1 研判 → B+ 通道 |
| S2 | 软联动 | Safety Rule 校验后通过 |
| S3 | 强联动 | Safety Rule 校验 + 人工确认 |

## 2. 三维组合规则

> **核心原则**：AI 必须 **三个维度同时允许** 才可执行；任何维度不允许 = 拒绝执行。

### 2.1 维度组合矩阵

| 技术 | 业务 | 安全 | 综合 | 是否允许执行 | 示例 |
|---|---|---|---|---|---|
| T0 | B0 | S0 | **拒绝** | ✗ | 无任何能力 |
| T1 | B1 | S1 | **展示** | ✓（L0/L1） | 数据展示 + L1 研判 |
| T2 | B2 | S2 | **受控** | ✓（L2 人工确认） | 模拟写入 + Safety Rule 通过 + 人工确认 |
| T3 | B3 | S3 | **白名单** | ✓（L3 白名单场景） | 真实写入 + 业务授权 + 强联动 |
| T3 | B4 | S2 | **拒绝** | ✗ | 即便技术可写、业务完全自动，安全不允许 |
| T2 | S0 | S0 | **拒绝** | ✗ | 安全红线 → 直接拒绝 |

### 2.2 渔业场景示例

| 场景 | 技术 | 业务 | 安全 | 综合 | 说明 |
|---|---|---|---|---|---|
| F-01 夜间低氧增氧 | T3 | B2（默认）/ B3（白名单） | S2 / S3 | 受控 / 白名单 | Safety Rule + 人工确认；白名单场景可 L3 |
| F-02 动态投喂 | T2（推荐） | B2 | S2 | 受控 | 任务规划 → 人工触发 → 沙箱验证 → 真实下发 |
| F-04 多模态预警 | T1 | B1 | S1 | 展示 | 仅识别 + 通知，不执行 |
| F-05 数据归集 | T1 | B1 | S1 | 展示 | NL 查询 + 自动报告 |

### 2.3 粮库场景示例

| 场景 | 技术 | 业务 | 安全 | 综合 | 说明 |
|---|---|---|---|---|---|
| G-01 粮情研判 | T1 | B1 | S1 | 展示 | L1 研判 + 通知，不执行 |
| G-02 数据可信度 | T1 | B1 | S1 | 展示 | 漂移识别 + 可信度评分 |
| G-03 通风/气调寻优 | T2（推荐） | B2 | S2 | 受控 | 寻优 + 人工确认；真实写入需原硬联锁 + 原系统厂商授权 |
| G-04 出入库调度 | T2 | B2 | S2 | 受控 | 任务规划 + 人工确认 |
| **G-05 熏蒸安全** | **T0/T1** | **B0/B1** | **S0** | **拒绝** | **Agent 不得控制熏蒸；原硬联锁独立触发** |
| **G-05 熏蒸 B+ 通知** | **T1** | **B1** | **S1** | **展示** | Agent 仅做 L1 研判 + 通知 + 留痕 |
| G-07 多模态安防 | T1 | B1 | S1 | 展示 | 仅识别 + 预案匹配 |

> **关键约束**：门禁、熏蒸、声光告警、应急逃生等原硬联锁动作 → **S0 强制禁止**；任何 T ≥ T1 的尝试都必须 fail-closed。

## 3. 与 PRD Level 0–4 的映射

| PRD Level | 综合权限 | 含义 |
|---|---|---|
| L0 | T1 + B1 + S1 | 仅展示 |
| L1 | T1 + B1 + S1 | 提醒 / 研判 |
| L2 | T2 + B2 + S2 | 建议 + 人工确认 |
| L3 | T3 + B3 + S3 | 白名单自动执行 |
| L4 | T3 + B4 + S? | 完全自动（不允许） |

> **重要区别**：Sol 建议"避免技术可执行 = 业务允许执行"。本模型在 L2/L3 上做了技术 / 业务 / 安全的"AND"逻辑；L4 永远不允许进入 Demo/Pilot。

## 4. 权限审批与冻结

### 4.1 权限矩阵（v0.4 新增）

| 维度 | Demo 阶段 | Pilot 阶段 | 升级条件 |
|---|---|---|---|
| T2 | 默认允许（沙箱） | 默认允许（受控真实环境） | 沙箱测试 100% 通过 |
| T3 | 仅白名单场景 | 经安全 + 业务 + 技术三方签字 | 原硬联锁独立性测试通过 |
| B2 | 默认允许 | 默认允许 | 人工角色培训完成 |
| B3 | 仅白名单场景 | 业务签字 | 业务 KPI 签字 |
| S2 | 默认允许 | 默认允许 | Safety Rule 测试通过 |
| S3 | 仅粮库门禁 / 熏蒸 / 通风受控场景 | 三方签字 + 监管备案 | Q1 / Q5 闸门通过 |

### 4.2 权限升级流程

1. **申请**：由 AI 工程师提出 → 写明场景 / 维度 / 等级；
2. **评审**：技术负责人（技术）+ 业务负责人（业务）+ 安全工程师（安全）；
3. **审批**：项目经理签字 + 安全合规负责人会签；
4. **冻结**：进入 `09_AI价值机会画像.md` §3 ROI 指标 + `08_合规监管与责任画像.md` §5 Pilot Gate；
5. **审计**：每次执行写入 `审计日志`，符合 `COMMON-NFR-001` 要求。

### 4.3 权限降级与熔断

- **数据缺失 / 漂移**：T 维度降级到 T1；Safety Rule 触发 → 全维度降级到 S0；
- **模型置信度不足**：B 维度降到 B1；
- **接口异常**：T 维度降到 T1；
- **任一维度降级到 0**：综合权限 = 拒绝；
- **Safety Rule Engine 故障**：通道 A fail-closed，通道 B 独立运行（参见 PRD §9.4.1）。
