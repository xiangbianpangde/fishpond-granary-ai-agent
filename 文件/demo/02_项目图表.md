## 画法约定

### Archify JSON IR（本次采用）

- 支持 5 种 `diagram_type`：`architecture`、`workflow`、`dataflow`、`sequence`、`lifecycle`。
- 通过 `/talk arch` 风格和本地渲染器生成 HTML、SVG，再用 `talk_export png` 导出 PNG。
- 约束包括：节点标签不超过默认宽度、检查布局避免标签和连线重叠、列数不超过 5、行数不超过 4。
- 适用于安全、权限、并行分支等需要准确表达关系的图表。

### Mermaid（本次弃用）

Mermaid 仍适合简单流程，但本项目的双通道、安全链路和并行分支容易出现布局混乱，也不易清楚区分“硬安全通道”和“AI 决策链”。因此，本项目的复杂图表统一使用 Archify；验证矩阵、需求表和对比表继续使用 Markdown。

### 决策原则

- **优先使用 Archify**：涉及安全、权限、并行关系和异常分支的图。
- **保留 Markdown 表格**：验证矩阵、需求表和对比表等结构化数据。

## 渲染命令参考（用于复现或微调）

```bash
# 通过 pi /talk 切换 arch 风格
talk_set_style({ styleId: "arch" })

talk_render({
  styleId: "arch",
  title: "图 3 · 渔业智能体闭环流程图",
  content: "<Archify JSON IR>",
  surface: "main"
})
talk_export({
  format: "png",
  out: "./charts/03-渔业闭环.png",
  surface: "main"
})
```

### Archify JSON IR 的团队维护

> v0.2 的 §90 曾指向本机临时路径 `~/.pi/agent/talk/sessions/...`，不利于版本控制。

现在的做法是在每个 `charts/<chart>.md` 末尾追加折叠代码块，直接保存 Archify JSON IR。这样可以：

1. **版本控制**：图表的 IR、说明和 PNG 使用同一份源文件维护；
2. **复现**：团队成员可以用同一份 JSON 重新渲染；
3. **持续调整**：后续修改不依赖某个成员的本机会话记录。

**模板**：在每个 `charts/*.md` 末尾追加：

````markdown
<details>
<summary>📐 Archify JSON IR（可复现 / 可调整）</summary>

```json
{ ... Archify JSON ... }
```

</details>
````

> **外层使用四个反引号的原因**：````markdown` 与内层 ```json` 不会互相提前关闭代码块。
