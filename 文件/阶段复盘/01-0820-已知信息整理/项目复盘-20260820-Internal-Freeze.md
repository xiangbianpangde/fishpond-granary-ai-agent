## 3. 关键技术决策（冻结要点）

### 3.1 三层独立安全架构

```
通道 A：业务智能（可使用大模型）
  专业模型 + 知识库 → AI Agent → Safety Rule Engine → 自动化等级 → 原设备控制

通道 B：原有硬安全（完全独立，不依赖大模型或 Safety Rule）
  现场已有信号 → 原系统硬安全联锁 → 安全动作

通道 B+：软件辅助（可使用大模型和 Safety Rule，但不替代 B）
  同样的事件流 → Safety Rule Engine → 软件补充、通知和审计
```

**核心原则**：
- AI **永远不能绕过**原硬联锁；
- Safety Rule Engine 故障时，**通道 A 必须停止执行（fail-closed）**，严禁 Tool Calling 和设备控制；
- 通道 B 与 A **没有执行依赖**。

### 3.2 AI/Agent 认知与编排承接率（原“60–80%”接管率）

```
= Demo 后由 AI/Agent 承接的判断和任务安排步骤数 ÷ Baseline 工作流中的全部判断、任务安排步骤 + 强制保留的人工审批步骤
```

**边界**：
- ❌ 不计入分母：纯物理执行、原硬联锁动作和 Safety Rule 独立动作；
- ✅ 计入分母：强制人工审批（不计入分子，因为这是刻意保留的环节）；
- 分子只包含由 AI/Agent 承接的判断和任务安排步骤。

**目标**：Demo ≥ 60%；Stretch ≥ 80%；冻结安全负例测试集内危险动作错误放行率 = 0，安全负例阻断率 = 100%。

### 3.3 BASE / SCENE 需求分级

- **P0-BASE**（9 条）：项目级硬要求，**不依赖场景选型**，全部属于共用底座；
- **P0-SCENE**（19 条）：候选场景入选后激活，只对对应场景生效，避免提前冻结；
- **P1**（29 条）：能提升 Demo 说服力，但不阻塞项目级验收。

## 4. 流程经验与教训

### 4.1 先把用户提示词问清楚（本次最大教训）

**初期**：用户提示词较粗，没有说明需要哪些图表、PRD 应包含什么、对比分析的范围和“项目需求”的含义，导致前两轮反复确认。

**对策**：从第二轮开始使用 `/sol` 作为外部顾问，先向用户确认一个最关键的问题（范围、读者或颗粒度），再补全结构，最后执行产出。

### 4.2 oracle worker 故障（本轮新增）

**症状**：oracle worker 等待“Copy 按钮数量 > assistant 条数”这一条件时偶尔卡住，任务一直停在 `awaiting_response`。

**解决**：已修复完成条件，改为确认“Stop answering 消失且 Send 可重新点击”；轮询间隔改为 10–15 秒。

**本轮损失**：6 次 oracle 派遣失败，用户最终从网页取回 1 次回复。

### 4.3 文件级同步问题

**第二轮教训**：changelog 写了“已修”，**但实际文件没有改**，尤其是 GRAN-INT-001，修了两轮才真正落地。oracle 通过关键词搜索定位到问题。

**对策**：每次编辑后都要重新 read 验证，不能假设 edit 成功就代表内容已经同步。

### 4.4 10 文件上限

oracle 每批最多提交 10 个文件，8 张图（每张包含 `.md` + `.png`）需要分两批。

**对策**：Batch 1 提交主文件、audit 和 3 张关键图；Batch 2 提交其余 5 张图。

### 4.5 图表工具切换

**v0.2 → v0.3**：从 Mermaid 切换到 `/talk arch`（Archify JSON IR）。
- Mermaid 不容易表达安全语义、并行分支和双通道；
- Archify 可以精确控制子图、节点和连线，并输出 SVG，更适合技术架构图。
